# Приложение ТигрБанк

## Предметная область 

Данный проект реализует часть приложения ТигрБанк, а именно – модуль «Учет финансов». В модуле реализованы:

- управление счетами, категориями и операциями: создание, редактирование, удаление, просмотр;
- аналитика по операциям за выбранный период, по доходам и расходам в категориях;
- импорт и экспорт данных в различных форматах: CSV, JSON, YAML;
- подсчет времени выполнения некоторых функций.

## Архитектура решения

В данном приложении все поделено на модули и классы:

Модуль `model` предназначен для базовых классов, которые описывают модели сущностей из предметной области:

- `BankAccount`
- `Category`
- `Operation`

Модуль `repository` отвечает за хранение и обращение к данным базовых классов:

- `BankAccountRepository`
- `CategoryRepository`
- `OperationRepository`

В модуле `service` сосредоточена вся бизнес-логика:

- классы `BankAccountService`, `CategoryService`, `OperationService` реализуют управление сущностями базовых классов: CRUD-операции и расчеты.
- в модуле `file.exchange` содержится логика импорта/экспорта данных, при этом класс `ExchangeService` отвечает за обработку данных для импорта/экспорта.
- `ReportService` отвечает за генерацию аналитики по операциям.

Модуль `controller` отвечает за взаимодействие с пользователем и управляет приложением:

- `BankController` — главный контроллер, объединяющий работу обработчиков из модуля `handler`.
- модуль `handler` обрабатывает консольный ввод/вывод и общается с классами из `service`.

## Принципы SOLID и DI-контейнер

Проектирование приложения выполнялось с соблюдением SOLID-принципов.

### Single Responsibility Principle

Каждый класс имеет одну четко определенную причину для изменения.

Пример этого принципа видно по структуре проекта, например:

- `BankAccount` отвечает только за структуру данных счета
- `BankAccountRepository` отвечает только за хранение и доступ к объектам счетов
- `BankAccountService` реализует бизнес-логику, обеспечивает целостность данных, которые попадают в хранилище
- `BankAccountHandler` отвечает за взаимодействие с пользователем

### Open/Closed Principle

Поведение системы можно расширять, не внося или внося минимальные изменения в существующий код.

Например, для добавления профилирования был сделан интерфейс `IOperationService` и класс `ProfilingOperationService` – так удалось расширить функционал `OperationService`, не меняя ничего в этом сервисе.

Еще можно привести в пример классы импорта/экспорта: на `ExchangeService` никак не повлияет добавление новых провайдеров других форматов, так как он работает с интерфейсом `IExchangeProvider`.

### Liskov Substitution Principle

Объекты подклассов могут заменять объекты базовых классов без нарушения работы программы.

Например, обработчику `OperationHandler` без разницы, с кем работать – с классом `OperationService` или с классом-профилировщиком `ProfilingOperationService`, потому что обработчик использует интерфейс `IOperationService`.

### Interface Segregation Principle

В системе используются мелкие интерфейсы вместо одного большого.

Например, интерфейс `IExchangeProvider` создан исключительно для импорта/экспорта файлов.

### Dependency Inversion Principle

Модули верхних уровней не зависят от модулей нижних уровней.

В данном приложении зависимости внедряются через конструкторы. 

### DI-контейнер

В проекте реализован DI-контейнер для управления зависимостей с помощью Spring Boot. Spring автоматически связывает элементы приложения благодаря аннотациям `@Service`, `@Repository`, `@Component` и другим.

## Преимущества и недостатки

### Преимущества введенных абстракций

Введенные интерфейсы и абстрактные классы улучшили архитектуру решения:

- `IOperationService` позволил добавить профилирование операций через `ProfilingOperationService` без изменения `OperationService`.
- `IExchangeProvider` снижает связанность между логикой управления данными и конкретными форматами файлов: можно легко добавлять новые форматы, не переписывая `ExchangeService`.
- Можно легко писать модульные тесты как для существующего, так и для нового функционала.

### Возможные проблемы расширения

В текущем решении есть упрощения, которые могут вызвать проблемы при масштабировании системы:

- Профилирование применено только для нескольких методов `OperationService`. Для обеспечения вычисления времени выполнения всех операций в программе потребуется внедрить интерфейсы для каждого сервиса, затем обернуть их в декораторы.
- Аналитические отчеты отображаются только в консоли. Для реализации других форматов потребуется написать логику формирования в отдельной абстракции.
- Идентификатор объекта реализован с помощью простого инкремента в сервисах, что может привести к его дублированию.

## Заметки по реализации функциональности

### CRUD-операции

Операции удаления и редактирования реализованы в сервисах и успешно протестированы в модульных тестах, но отсутствуют в консольном интерфейсе, чтобы его не перегружать.

### Аналитика

Подсчет разницы и группировка по категориям выполняются для конкретного счета, а не для всех счетов сразу. Это сделано осознанно, так как такая аналитика информативнее для пользователя.

### Импорт/экспорт

Файлы обмена по умолчанию сохраняются в корневой директории проекта и ищутся там же. 

В корне уже подготовлены демо-файлы с примерами данных, которые можно использовать для первичной проверки функционала импорта сразу после запуска.

### Пересчет баланса

Пересчет баланса (`updateBalance()` в `OperationService`) реализован только автоматически. Вызывается при добавлении, редактировании или удалении операции.

### Статистика

Профилирование реализовано только для основных операций `OperationService`.
