# Приложение ТигрБанк

## Предметная область 

Данный проект реализует часть приложения ТигрБанк, а именно – модуль «Учет финансов». В модуле реализованы:

- управление счетами, категориями и операциями: создание, редактирование, удаление, просмотр;
- аналитика по операциям за выбранный период, по доходам и расходам в категориях;
- импорт и экспорт данных в различных форматах: CSV, JSON, YAML;
- подсчет времени выполнения некоторых функций.

## Архитектура решения и используемые паттерны

В данном приложении все поделено на модули и классы:

Модуль `model` предназначен для базовых классов, которые описывают модели сущностей из предметной области:

- `BankAccount`
- `Category`
- `Operation`

Также в этом модуле лежат реквесты для дальнейшего использования в паттерне «Команда».

Модуль `repository` отвечает за хранение и обращение к данным базовых классов:

- `BankAccountRepository`
- `CategoryRepository`
- `OperationRepository`

В модуле `service` сосредоточена вся бизнес-логика, организованная с помощью паттернов «Фабрика», «Фасад» и «Команда»:

- модуль `factory` реализует паттерн «Фабрика», содержит интерфейсы (`IBankAccountFactory`, `ICategoryFactory`, `IOperationFactory`) и их реализации в `impl` для создания объектов сущностей.
- в модуле `facade` содержатся фасады `BankAccountFacade`, `CategoryFacade`, `OperationFacade`, `ReportFacade`, которые предоставляют интерфейс для взаимодействия консольных обработчиков с бизнес-сервисами и командами.
- модуль `command` инкапсулирует все пользовательские сценарии с помощью команд, за выполнение которых отвечает `CommandExecutor`.
- модуль `dto` содержит объекты для формирования аналитических отчетов (`PeriodicReport`, `GroupedCategoriesReport`).
- в модуле `file.exchange` содержится логика импорта/экспорта данных, реализованная через «Шаблонный метод».

Сервисы реализуют низкоуровневую логику управления сущностями:

- классы `BankAccountService`, `CategoryService`, `OperationService` управляют сущностями базовых классов (CRUD-операции и расчеты).
`ExchangeService` отвечает за обработку данных для импорта/экспорта.
- `ReportService` отвечает за генерацию аналитики по операциям.

Модуль `controller` отвечает за взаимодействие с пользователем и управляет приложением:

- `BankController` — главный контроллер, объединяющий работу обработчиков из модуля `handler`.
- модуль `handler` обрабатывает консольный ввод/вывод и общается с классами из `service`.

## Принципы SOLID, GRASP и DI-контейнер

Проектирование приложения выполнялось с соблюдением SOLID-принципов.

### Single Responsibility Principle

Каждый класс имеет одну четко определенную причину для изменения.

Пример этого принципа видно по структуре проекта, например:

- `BankAccount` отвечает только за структуру данных счета
- `BankAccountRepository` отвечает только за хранение и доступ к объектам счетов
- `BankAccountService` реализует бизнес-логику, обеспечивает целостность данных, которые попадают в хранилище
- `BankAccountHandler` отвечает за взаимодействие с пользователем

### Open/Closed Principle

Поведение системы можно расширять, не внося или внося минимальные изменения в существующий код.

Например, на сервис по экпорту/импорту данных `ExchangeService` никак не повлияет добавление новых провайдеров других форматов, так как он работает с интерфейсом `IExchangeProvider`.

### Liskov Substitution Principle

Объекты подклассов могут заменять объекты базовых классов без нарушения работы программы.

Например, классу `CommandExecutor` не важно, с какой командой работать – с `CreateCategoryCommand` или `ExportCommand`, так как они все используют интерфейс `Command`.

### Interface Segregation Principle

В системе используются мелкие интерфейсы вместо одного большого.

Например, интерфейс `IExchangeProvider` создан исключительно для импорта/экспорта файлов.

### Dependency Inversion Principle

Модули верхних уровней не зависят от модулей нижних уровней.

В данном приложении зависимости внедряются через конструкторы. 

### GRASP

В проекте используются ключевые идеи GRASP: High Cohesion и Low Coupling.

#### High Cohesion

Данный принцип соблюдается благодаря:

- четкому разделению на модули и классы, у всех свои конкретные задачи.
- паттерну «Команда», который делит пользовательские сценарии на отдельные классы (`CreateAccountCommand`, `UpdateAccountNameCommand` и др.).

#### Low Coupling

Принцип «низкого связывания» соблюдается благодаря:

- паттерну «Фабрика», который изолирует процесс создания объектов. Сервисы работают только с интерфейсами фабрик (`IBankAccountFactory` и др.), не зная о конкретных реализациях в `impl`.
- паттерну «Фасад», который выступает единым посредником между обработчиками в контроллере и сервисами. Обработчик (`BankAccountHandler` и др.) взаимодействует только с одним фасадом (`BankAccountFacade` и др.).

### DI-контейнер

В проекте реализован DI-контейнер для управления зависимостей с помощью Spring Boot. Spring автоматически связывает элементы приложения благодаря аннотациям `@Service`, `@Repository`, `@Component` и другим.

## Преимущества и недостатки

### Преимущества введенных абстракций

Введенные интерфейсы и абстрактные классы улучшили архитектуру решения:

- `IOperationService` позволил добавить профилирование операций через `ProfilingOperationService` без изменения `OperationService`.
- `IExchangeProvider` снижает связанность между логикой управления данными и конкретными форматами файлов: можно легко добавлять новые форматы, не переписывая `ExchangeService`.
- Можно легко писать модульные тесты как для существующего, так и для нового функционала.

Внедрение паттернов проектирования улучшило архитектуру решения:

- Интерфейс `ICommand` и класс `CommandExecutor` инкапсулировали логику операций, что позволяет исполнителю выполнять любую команду: как `CreateCategoryCommand`, так `ExportCommand`.
- Паттерн «Фасад» упростил доступ к сложной бизнес-логике, скрыв детали вызовов сервисов и команд.
- Паттерн «Фабрика» позволил гибко создавать объекты, не привязывая основной код к конкретным классам реализации.
- Шаблонный метод для работы с файлами исключил дублирование кода для различных форматов, оставив им только реализацию парсинга.
- `IExchangeProvider` снижает связанность между логикой управления данными и конкретными форматами файлов: можно легко добавлять новые форматы, не переписывая `ExchangeService` и `ExchangeProvider`.
- Можно легко писать модульные тесты как для существующего, так и для нового функционала.

### Возможные проблемы расширения

В текущем решении есть упрощения, которые могут вызвать проблемы при масштабировании системы:

- Аналитические отчеты отображаются только в консоли. Для реализации других форматов потребуется написать логику формирования в отдельной абстракции.
- Идентификатор объекта реализован с помощью простого инкремента в сервисах, что может привести к его дублированию.

## Заметки по реализации функциональности

### CRUD-операции

Все CRUD-операции реализованы.

### Аналитика

Подсчет разницы и группировка по категориям выполняются для конкретного счета, а не для всех счетов сразу. Это сделано осознанно, так как такая аналитика информативнее для пользователя.

### Импорт/экспорт

Файлы обмена по умолчанию сохраняются в корневой директории проекта и ищутся там же. 

В корне уже подготовлены демо-файлы с примерами данных, которые можно использовать для первичной проверки функционала импорта сразу после запуска.

### Пересчет баланса

Пересчет баланса (`updateBalance()` в `OperationService`) реализован только автоматически. Вызывается при добавлении, редактировании или удалении операции.

### Статистика

Профилирование реализовано для всех пользовательских сценариев в классе `CommanExecutor`. При выполнении действия в консоли отображается его название и время выполнения.
